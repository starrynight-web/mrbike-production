# MrBikeBD — Complete Production Audit Report
**Date:** 2026-03-22 | **Auditor:** Senior Architect / DevOps / Security / SEO Review

## 0. EXECUTIVE SUMMARY

**What it does:** MrBikeBD is a full-stack motorcycle marketplace platform for Bangladesh. Users can browse official bike specs/prices, list used bikes for sale, compare bikes, read news articles, and manage a profile/wishlist.

**Architecture:** Hybrid monolith — Django 4.2 REST backend + Next.js 16 frontend, deployed separately (Render.com + Vercel).

**Tech Stack:**
- Backend: Django 4.2, DRF 3.15, PostgreSQL, Redis, Cloudinary, Brevo SMTP, Django-Q2, Sentry
- Frontend: Next.js 16 (App Router), React 19, Zustand, TanStack Query, Radix UI, Framer Motion, next-auth v4

**Key Strengths:**
- Solid JWT + 2FA auth implementation for admin
- Good indexing strategy on core models
- ISR/SSG via Next.js App Router for SEO
- Sentry + structured JSON logging enabled
- CSP, HSTS, CORS, and security headers configured
- Cloudinary image processing with WebP conversion

**Critical Risks:**
1. **Hardcoded admin email** `mrbikecloude@gmail.com` in `users/views.py:368` — credential in source code
2. **Rate limiting is effectively disabled** (`999999/hour`) for all scopes
3. **`SECRET_KEY` can be auto-generated by Render** on each deploy, invalidating all sessions/tokens
4. **`DEBUG_OTP=False` flag not implemented** — no code branches on it
5. **No test coverage** — [tests.py](file:///e:/mr/backend/apps/bikes/tests.py) files are empty stubs
6. **[.env.example](file:///e:/mr/.env.example) duplicated** with contradictory MongoDB + PostgreSQL configs (dead context)

**Production Readiness:** **Beta** — architecture is sound, but critical security and reliability gaps block production sign-off.

## 5. DATA FLOW & REQUEST LIFECYCLE

```
User Action → Axios (frontend) → Next.js API proxy OR direct backend fetch
    → Django URL router → ViewSet/APIView
    → JWT Authentication (simplejwt)
    → Permission check (AllowAny / IsAuthenticated / IsSuperAdminOnly)
    → Serializer validation
    → Service layer (if exists) or direct ORM
    → PostgreSQL query
    → Serializer response → StandardResponse envelope
    → JSON → TanStack Query cache → React re-render
```

**Data Fetching Patterns:**
- Server components use `apiServer.get()` (Node.js fetch with `cache: 'no-store'` or revalidate)
- Client components use TanStack Query + axios
- Mixed pattern — some pages double-fetch (SSR + client hydration)

**Async Handling:** Django-Q for background tasks (expiry checks, email sends). Email sending is synchronous in views (registration, password reset) — blocks request thread.

**Retry Logic:** None implemented in frontend axios calls or backend email sends.

**Race Conditions:**
- `views_count` increment uses [F('views_count') + 1](file:///e:/mr/backend/apps/users/views.py#291-332) ✅ (correct atomic update)
- Slug uniqueness check in `UsedBikeListing.save()` uses a while loop — race condition possible under concurrent saves (should use `select_for_update()`)

## 7. AUTHENTICATION & AUTHORIZATION

**System:** JWT (simplejwt) + next-auth v4 (frontend session)
- Access token: 60 min
- Refresh token: 7 days, rotated + blacklisted ✅

**Login Flow:**
1. Email/password → [EmailLoginView](file:///e:/mr/backend/apps/users/views.py#215-289) → JWT issued
2. Google OAuth → [GoogleAuthView](file:///e:/mr/backend/apps/users/views.py#72-153) → JWT issued
3. Admin email triggers 2FA (Email OTP or TOTP)

**2FA Implementation:** 
- Email OTP stored in Redis cache with 5-min TTL ✅
- TOTP via `pyotp` ✅
- `hmac.compare_digest()` used for timing-safe OTP comparison ✅

**Critical Issues:**

| Issue | Severity |
|-------|----------|
| `mrbikecloude@gmail.com` hardcoded in `views.py:368` | **CRITICAL** |
| `SUPER_ADMIN_EMAIL` fallback default `admin@mrbikebd.com` in base.py if env not set | HIGH |
| `User.email` field is `null=True, blank=True` — email is the USERNAME_FIELD but can be null | HIGH |
| `IsEmailVerified` permission exists but not applied to all sensitive endpoints | MEDIUM |
| No brute-force lockout (rate limiting disabled at `999999/hour`) | CRITICAL |

**RBAC:**
- Frontend: [proxy.ts](file:///e:/mr/frontend/proxy.ts) middleware checks `token.role === "admin"` ✅
- Backend: `IsSuperAdminOnly` permission class used on admin actions ✅
- Role escalation risk: `User.save()` auto-sets `is_staff=True` for `admin` and `moderator` roles — a malicious role change would grant Django admin access

## 13. SCALABILITY ANALYSIS

**Stateless:** JWT auth — backend is stateless ✅ (horizontal scaling possible)

**Current bottlenecks:**
1. Gunicorn 3 workers on Render free (512MB RAM) — max ~30 concurrent requests
2. Synchronous email in request path blocks worker threads
3. Single Django-Q worker — task queue not redundant
4. Free PostgreSQL on Render — 1GB storage, no replicas, shared compute
5. No Redis Sentinel/Cluster — single Redis instance is a SPOF

**Scaling Path:**
- Render free → Render Starter ($7/mo): 512MB → 2GB RAM, 0.5→1 vCPU
- Add `--workers 9` (2×CPU+1) and `--worker-class gevent` for I/O concurrency
- Move to PgBouncer or Supabase for connection pooling at scale
- Move email to Django-Q tasks (already configured)
